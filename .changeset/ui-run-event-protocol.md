New package `@effect-uai/ui`: agentic UI primitives for effect-uai apps. This first release ships the wire protocol.

- `RunEvent`: Effect Schemas for every event a server streams about agent runs (run lifecycle with exactly one terminal per run, steps, text, refusal and reasoning deltas, citations, images, structured objects, tool calls and results, usage, persisted `data` and transient `live` payloads, and the stream-scoped `input-accepted` echo a queueing server sends), wrapped in an `Envelope { streamId, seq, runId?, event }`. `EnvelopeJson` is the derived JSON codec for the wire, so image bytes and other non-JSON values encode safely.
- `Input`: what a client sends. Transports and atoms accept any input with a client-generated `InputId` (for optimistic UI); the preset is `submit` (one or more core user messages, so they enter the loop's history unchanged) and `resolve` (approvals). Constructors build drafts; `Atoms.submit` (or `Input.withId`) assigns a UUIDv7 id from `effect/crypto`'s `SecureRandom`. `Input.make(DataSchema)` adds typed app `data` the server interprets (template ids, model choice); `InputJson` carries image bytes over JSON.
- Branded ids: `StreamId`, `RunId` and `InputId` are branded Schemas, so wire decoding brands them and they can't be swapped by accident.
- `Projection`: maps an effect-uai loop (`TurnEvent`, `ToolEvent`, tool outputs) onto `RunEvent`s as a fold pair (`initial`, `step`) plus the `toRunEvents` operator. Each model turn becomes a step; reasoning is a signal by default (`reasoning: "summary" | "full"` forwards more); `providerData` never leaves the server.
- `RunView`: the client's view of one run as plain data, folded with `initial` + `step` (use with `Stream.scan` or `Stream.runFold`). Ordered blocks in core's shapes where they exist (`output_text` with its citations as `annotations`, `output_image`, `refusal`) plus reasoning, tool calls with status, structured objects via JSON Patch, and data; transient `live` values, summed usage, and selectors (`text`, `refusal`, `isBusy`, `objects(view, name, Schema)`). Idempotent on `seq`, so replays after a reconnect are safe.
- `Thread`: an optional chat fold over `RunView`. `Thread.make({ user, settle, decodeInput })` builds it for any entry types (`{ role, id, value }`); the module's own `initial` / `step` / `submitted` / `ended` are the default preset (the input's messages, the run's `RunView`). A fold spreads straight into `Atoms.make` / `Atoms.session`. Input sent while a run is active, or echoed by the server (`input-accepted`), waits in `pending` until a `run-started` lists it (one run may answer several inputs); `hasInput`, `truncateAfter` for regenerate/edit, `State(user, assistant)` for a Schema of the state, and `toHistory` (lossy; keep history on the server). `seq` is deduplicated per stream, so one stream per run and one stream per chat both work, and stream-scoped frames (no `runId`) never land inside a run.
- `Encoding`: SSE framing (`id` = seq, `event` = type, `data` = envelope JSON) with `toSSE` / `fromSSE` over core's `SSE`, `responseHeaders`, and `lastEventId(headers)` (the standard `Last-Event-ID` header a reconnecting EventSource sends). NDJSON uses core's `JSONL` with `RunEvent.EnvelopeJson`.
- `Client`: browser-safe envelope sources over `effect/http`'s `HttpClient` (`sse`, `ndjson`) and `resumable`, which reconnects from the last `seq` on a `Schedule` and drops duplicates. `until: "terminal"` (default) follows one run and treats a connection that closes before the terminal as a drop; `until: "never"` follows a session stream that carries many runs.
- `Transport`: how a client reaches the server. Per run: `direct` (one request per input, the body is the run), `durable` (submit returns a stream id, events are read from `after`, with `resume` and `stop`), and `local` (the agent runs in-process). Per session: `session` (a durable chat: `send` without a stream id starts one, with one adds a run to it; `events` follows the whole session; the stream id is the app's own chat id). Over HTTP, `direct`, `durableHttp` and `sessionHttp` take effectful request builders (so a body can be Schema-encoded), and `durableHttp` and `sessionHttp` (no route convention), read the id from the response JSON, parse SSE and reconnect from the last `seq`. Any other source (RPC, server functions) is a transport too: a plain `{ start: (input, state) => stream }`.
- `Atoms`: framework-neutral state on `effect/reactivity`. `make` takes any fold plus a per-run transport and returns `state`, `submit`, `stop` and `resume` (typed as present for durable transports); `busy: "block" | "stop-then-submit"` is required; `thread` is the `Thread` preset. `session` takes a session transport and returns `state`, `open(chatId)`, `submit`, `stop`; `chat` is the `Thread` preset, where input sent during a run waits as pending for a server that queues. React reads them with `@effect/atom-react`.
- `Run`: server-side stream helpers. `withTerminal` brackets a run with `run-started` and exactly one terminal on every exit path (`stopWhen` gives `run-stopped`, failures become `run-failed` with a `retryable` flag); `sequence` assigns per-stream `seq` and the open run's id; `coalesce` merges adjacent deltas within a time window.
