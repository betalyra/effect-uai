---
title: Migrating to 0.20
description: Reconnecting moves from the HTTP transport helpers to Transport.reconnect, a session stream that ends now fails with Disconnected, and Effect 4.1 is the minimum.
---

0.20 fixes gaps in `@effect-uai/ui`'s durable transports. Reconnecting moves
out of `sessionHttp` / `durableHttp` into `Transport.reconnect`, which works
for any session or durable transport and no longer retries errors that won't
go away (a deleted chat, an expired login).

Only apps on durable transports (`Transport.session`, `sessionHttp`,
`Transport.durable`, `durableHttp`) and adapters that build a
`JobState.Failed` change code. Everything else is additive.

**Suggested order:** bump Effect, then move `reconnect`, then run typecheck.

## Effect 4.1

The `effect` peer range is now `>=4.1.0 <5.0.0`: `Transport.reconnect` uses
`HttpClient.isTransientError`, new in 4.1.

## `reconnect` moved to `Transport.reconnect`

```ts
// before
const transport = Transport.sessionHttp({
  send,
  events,
  stop,
  reconnect: Schedule.spaced("1 second"),
})

// after
const transport = Transport.reconnect(Transport.sessionHttp({ send, events, stop }))
```

The same for `durableHttp`. `Transport.reconnect` also takes
`Transport.session` / `Transport.durable` over any stream (WebSocket, RPC),
which had no reconnect before.

What it retries changed. The old option retried every error on its schedule;
`Transport.reconnect` retries a drop, a timeout, a transport error,
408 / 429 / 5xx and an SSE `retry:` line, waiting at least the server's
`Retry-After` / `retry:`. Anything else (404, 401, a malformed frame) ends the
stream with that error, in the `open` / `resume` atom's result. To keep
retrying one of your own errors, pass `while`:

```ts
Transport.reconnect(transport, { while: (error) => error._tag === "SocketClosed" })
```

The default backoff is exponential from 500 ms, capped at 10 s, with jitter.
To keep a fixed interval, pass `schedule: Schedule.spaced("1 second")`; to cap
the attempts in a row, `times`.

## Behavior change: a stream that ends early fails with `Disconnected`

A session stream never ends on its own, and a durable run's stream ends with
the run's terminal. `Transport.session` / `Transport.durable` (and the HTTP
helpers) now fail such a stream with `Client.Disconnected` when it completes
early, where it used to complete quietly and leave the chat no longer
followed. With `reconnect`, a `Disconnected` is retried; without it, the
`open` / `resume` atom fails and `ended(…, "disconnected")` runs.

The transports' error types include `Client.Disconnected`. If you match on
them exhaustively, add the case.

## `Durable` has `submit`

`Transport.Durable` now carries `submit`, and `start` is `submit` followed by
`resume(streamId, 0)`, so `reconnect` can rebuild it without sending an input
twice. Transports built with `Transport.durable` / `durableHttp` get it for
free; a `Durable` you write by hand needs `submit`.

## `JobState.Failed` carries an error

Only adapter authors who build `JobState` change code. `Failed` now holds
the error the adapter classified the provider's failure as, instead of a
reason string, so a refusal can surface as `ContentFiltered` rather than
always `GenerationFailed`:

```ts
// before
JobState.Failed({ reason: wire.error.message, raw: wire })

// after
JobState.Failed({
  error: new AiError.GenerationFailed({ provider, message: wire.error.message, raw: wire }),
})
```

`collect` / `run` fail with that error as is. `JobState<A, E>` takes the
error type as a second parameter, defaulting to `AiError`.

## Behavior change: `Job.run` cancels on any failure

`Job.run` (and `DeepResearch.generate`, `VideoGenerator.generate`) used
to cancel the provider's job only when interrupted. It now cancels on any
exit but success, its own `Timeout` included, and also when interrupted
while the submit is still in flight. The ref never leaves `run`, so a
job it gave up on would otherwise run on, billed, for nobody. Use
`submit` + `collect` to keep a job you stopped waiting for.

## Additive

- `open({ streamId, after })` on `Atoms.session` / `sessionThread` follows a
  stream from a position, e.g. a chat loaded from your database; a bare id
  still means "from the start".
- `Atoms.sessionThread({ initial })` starts from that thread. It sets the
  state only; `open` follows the chat.
- `SseEncoding.heartbeat(interval)` interleaves SSE comments so proxies don't
  close an idle stream.
- `Client.resumable`'s `schedule` is optional: without one, an early end fails
  with `Disconnected` and nothing is retried.
- `@effect-uai/responses`: `reasoning.effort` accepts `none`, `minimal` and
  `xhigh` (`ReasoningEffort`).
- **Video generation** is new: `@effect-uai/core/VideoGenerator`, with
  providers in `@effect-uai/fal/FalVideoGenerator` and
  `@effect-uai/google/GeminiOmniVideoGenerator`. See
  [Video generation](/video-generation/).
- `Job`: `JobState` is a `Data.TaggedEnum` (constructors and matchers; the
  type is still a structural union), `Pending` takes an optional
  `queuePosition`, `Job.watch` streams every polled state, `Job.result`
  turns a (tapped) state stream into its outcome, `Job.own(provider)`
  rejects another provider's ref before a wire call, and `JobRef` /
  `Job.refSchema<A>()` decode persisted refs.
- The deep-research adapters fail `InvalidRequest` on another provider's
  ref, and an unreadable submit response is `GenerationFailed` rather than
  `Unavailable`, so `Retry` no longer resubmits a job the provider
  accepted.
