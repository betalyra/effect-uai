# Recipe media: showing what a recipe actually does

Deferred. Captured here so the analysis is not lost.

## The problem

Most recipes are read as code, but a handful produce something you have to
see or hear before the point lands. The docs page currently shows none of
it. Whatever we build has to work for any recipe, sit in a fixed vertical
budget so the code stays near the top, and not rot when a recipe changes.

## What each recipe would show

Split by what the output actually is, rather than by medium. Three quarters
of the recipes are text streaming in a terminal.

## Why terminal casts over video

For text output an asciicast is roughly 50 KB against 5 to 10 MB for the
equivalent mp4. Text stays selectable, scales to any width instead of
pixelating, and can be re-rendered into a different player later without
re-recording. Most importantly it can be regenerated by re-running the
recipe, so it does not go stale silently the way a recorded video does.

That leaves genuine video for exactly four: voice-loop, streaming-transcription,
browser-usability, radio-station. Everything with audio or a browser in it.

## How the recording could work

Nothing in the recipes checks `isTTY` (colours in `recipes/_shared/render.ts`
are unconditional ANSI), so **no PTY is needed**: a plain pipe capture keeps
the colours. No `node-pty` native dependency, no `asciinema` binary.

The open question, and the reason this is deferred: the user wants recording
to be fully external, so recipes stay untouched and any command can be
recorded, not just ones we have wired up. Two shapes:

1. **A wrapper script** that spawns any command, timestamps stdout chunks, and
   writes asciicast v2 (`[seconds, "o", "text"]` lines under a header). Around
   80 lines, no dependencies, works for any command. Does not capture a real
   terminal session, only the child's output.
2. **A session recorder** the user starts, runs anything inside, and stops,
   producing one file to drop on the page. This is what `asciinema rec` does
   and needs a PTY to be faithful.

Option 2 is closer to what was asked for. Worth checking whether `asciinema`
as an external tool is acceptable before writing our own PTY recorder.

Either way it needs:

- **Idle clamping**, the thing that makes it watchable. Clamping inter-chunk
  gaps to about 1.2s turns a six-minute run into forty seconds without
  cutting a character.
- **Scripted stdin** for the interactive ones (tool-call-approval,
  model-escalation): wait for a substring, send a line.
- **A budget**: hard timeout and max duration so a hung run does not sit
  there burning tokens.

## Rendering on the page

Commit the `.cast` as the source of truth, render an animated SVG from it at
build time, embed as a plain `<img>`. Zero runtime JS, no React island,
scales, looks right in a docs page. Upgrading to `asciinema-player` later
reads the same `.cast` with no re-recording.

## Wiring into the site

Recipe pages are the repo READMEs (`recipes/*/README.md`, globbed in
`webpage/src/content.config.ts`). They must stay `.md`: GitHub only
auto-renders `README.md`, not `.mdx`, and these are meant to be read on
GitHub too. So media goes through frontmatter, the way `source` and `icon`
already do, or by convention on a `media/` directory next to the recipe.

## Cost and CI

These hit live APIs and cost money, so recording cannot run per PR.
Recording is a manual local command run the way recipes are run today
(`op run --env-file=.env.dev -- ...`), artifacts committed. CI runs only a
staleness report: list recipes whose source is newer than their cast. A
warning, not a failure, so a prompt tweak does not block a merge but rot
stays visible.
