## 3. Endpoint and auth

- Gemini API: `wss://generativelanguage.googleapis.com/ws/google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContent?key=API_KEY` (api/live, get-started-websocket). The SDK templates `${apiVersion}` into the path.
- Ephemeral token: different RPC name: `wss://generativelanguage.googleapis.com/ws/google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContentConstrained?access_token=TOKEN`, or header `Authorization: Token TOKEN` (api/live "Ephemeral authentication tokens", get-started-websocket). Docs say tokens work "only with the v1beta version"; the SDK warns "ephemeral token support is in v1alpha only" and the official example client hardcodes `v1alpha...BidiGenerateContentConstrained`. Both versions appear to be accepted; UNVERIFIED which is canonical, prefer `v1beta` per docs and fall back to `v1alpha`.
- Token minting: `POST https://generativelanguage.googleapis.com/v1beta/auth_tokens` (API key auth) with `AuthToken` body; SDK `ai.authTokens.create({ config })`. Token value is `token.name` (format `auth_tokens/...` per SDK prefix check). Ephemeral tokens are Preview and Live-only.

| AuthToken field                                                               | Meaning                                                                                                                                             | Default                  |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `uses`                                                                        | how many sessions may be started; `0` = unlimited; resuming does not count                                                                          | 1                        |
| `expireTime`                                                                  | after this, messages in the session are rejected, may be closed preemptively                                                                        | now + 30 min, max < 20 h |
| `newSessionExpireTime`                                                        | after this, new sessions cannot be started                                                                                                          | now + 60 s, max < 20 h   |
| `bidiGenerateContentSetup` (SDK: `liveConnectConstraints: { model, config }`) | locked setup: model plus any config                                                                                                                 | none                     |
| `fieldMask` (SDK: `lockAdditionalFields`)                                     | empty mask + setup present = setup taken entirely from token, client setup ignored; non-empty mask = only those fields overwrite the client's setup | empty                    |

Within `expireTime` you reconnect every ~10 min using `sessionResumption` with the same token even when `uses: 1`.

- Vertex: `wss://{LOCATION}-aiplatform.googleapis.com/ws/google.cloud.aiplatform.v1.LlmBidiService/BidiGenerateContent` with header `Authorization: Bearer OAUTH_TOKEN`; billing must be enabled. Model in setup is the full resource name `projects/{p}/locations/{l}/publishers/google/models/gemini-live-2.5-flash-native-audio`.

## 6. Turn-taking and interruption

- Automatic VAD (default): server segments speech; start of activity interrupts (`START_OF_ACTIVITY_INTERRUPTS`); on interruption ongoing generation is cancelled and discarded, only what was already sent stays in history, server emits `serverContent.interrupted: true`, then `turnComplete`; pending function calls are dropped and `toolCallCancellation.ids` is sent. Client must immediately flush its playback queue (best-practices: "You must immediately discard your client-side audio buffer").
- Manual VAD: set `automaticActivityDetection.disabled: true`, wrap audio in `activityStart` / `activityEnd`; the server has no pre-speech buffer and no silence tolerance in this mode, so use >= 500 ms end-of-speech threshold client-side.
- Hybrid VAD: keep automatic VAD and send `audioStreamEnd: true` when the client detects end of speech to force finalisation.
- `NO_INTERRUPTION` disables barge-in.
- Mid-session text: `realtimeInput.text` (3.1 and 2.5); `clientContent` still works throughout on 2.5 but always interrupts generation. Sending `clientContent` on 3.1 after the first model turn is unsupported.
- Sequential tool calls on 3.1: the model produces no audio until `toolResponse` arrives.

## 7. Tools

| Tool                                   | 3.1 Flash Live                            | 2.5 Flash Live                              |
| -------------------------------------- | ----------------------------------------- | ------------------------------------------- |
| Function calling                       | sync only (`behavior` default `BLOCKING`) | sync and async (`behavior: "NON_BLOCKING"`) |
| Google Search (`{ googleSearch: {} }`) | yes                                       | yes                                         |
| Code execution                         | no                                        | no                                          |
| URL context                            | no                                        | no                                          |
| Google Maps                            | no                                        | no                                          |

- Declarations go in `setup.tools[].functionDeclarations[{ name, description, parameters, behavior? }]`. No automatic tool handling; client answers with `toolResponse`.
- Async (2.5 only): `FunctionResponse.scheduling` = `SILENT` (add to context, no generation), `WHEN_IDLE` (default, generate without interrupting), `INTERRUPT`; `willContinue: true` turns a call into a generator. The Live tools guide places `scheduling` inside `response: { result, scheduling }`; the REST schema has it as a top-level `FunctionResponse` field. Which one the server honours on the wire is UNVERIFIED (SDK types expose the top-level field).
- Search grounding runs as generated Python: `modelTurn.parts` carry `executableCode` and `codeExecutionResult` parts alongside audio; `serverContent.groundingMetadata` is populated.
- Multiple tools combine in one `tools` array (Search + functions example). Tools cannot change on an open connection (config immutable) but can be changed when resuming with a handle, since only `model` is fixed across resumption.

## 8. Session management

- Connection ~10 min hard limit; `goAway.timeLeft` arrives first (Vertex: 60 s before). Session limits without compression: 15 min audio, 2 min audio+video (128k context, 25 tok/s audio). With `contextWindowCompression` sessions are unbounded; compression truncates oldest turns at a USER boundary, keeps system instruction, costs a latency spike, so keep `triggerTokens` high.
- Resumption: send `sessionResumption: {}` from the start; store the latest `sessionResumptionUpdate.newHandle` whenever `resumable` is true; on `goAway` or drop, open a fresh WS and send `setup` with `sessionResumption: { handle }` plus the same (or modified, except model) config. Handles valid 2 h after termination (Gemini API); Vertex says 24 h with a ~10 min resumption window (contradictory, quoted as is). Resuming while the model was generating or executing tools loses data. Ephemeral tokens: resumption does not consume a `use`.
- Vertex `transparent: true` returns the client message index matching the snapshot so the client knows what to resend; the Gemini API reference has no such field (`lastConsumedClientMessageIndex` UNVERIFIED on Gemini API).
- Vertex additionally lets you push new system instructions mid-session via `clientContent` with `role: "system"`.
- Survives resume: conversation history and model context. Does not survive: anything not yet acknowledged before the drop; the WS itself, so the client re-sends `setup`.

## 9. Video and screen sharing

- Frames are sent as `realtimeInput.video` JPEG/PNG blobs, max 1 fps, recommended 768x768 (Vertex, Firebase). Vertex quotes 258 tokens/s of video at default resolution; `MEDIA_RESOLUTION_LOW` drops to 64 tokens per image (generate-content enum), the media-resolution page lists 70 tokens/frame for Gemini 3 video at unspecified/low/medium and 280 at high. Which table applies to Live 3.1 is UNVERIFIED.
- Screen sharing has no dedicated API: capture the screen, downscale, JPEG-encode, send at <= 1 fps through the same field (official example `mediaUtils.js` does exactly this).
- On 3.1 the default `TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO` means every frame between turns is billed; gate frame sending on speech activity or set `turnCoverage` explicitly.

## 10. `@google/genai` SDK surface and raw-WebSocket feasibility

- `const session = await ai.live.connect({ model, config: LiveConnectConfig, callbacks: { onopen, onmessage(LiveServerMessage), onerror, onclose } })`. `LiveConnectConfig` is flat: `responseModalities, speechConfig, systemInstruction, tools, temperature, topP, topK, maxOutputTokens, seed, mediaResolution, thinkingConfig, enableAffectiveDialog, realtimeInputConfig, inputAudioTranscription, outputAudioTranscription, sessionResumption, contextWindowCompression, proactivity, translationConfig, safetySettings, avatarConfig, explicitVadSignal, generationConfig, httpOptions, abortSignal`. The converter folds the generation knobs into `setup.generationConfig` and leaves the rest at setup level (section 4).
- `session.sendRealtimeInput({ audio | video | text | activityStart | activityEnd | audioStreamEnd | media })` wraps as `{ realtimeInput: ... }` (`media` maps to deprecated `mediaChunks`, skill file says do not use). `session.sendClientContent({ turns, turnComplete = true })`, `session.sendToolResponse({ functionResponses })`, `session.close()`, `session.conn` exposes the raw WebSocket. The SDK buffers messages until `setupComplete`, then replays them to `onmessage`; it parses string, Blob and ArrayBuffer frames with `JSON.parse`.
- Browser: works with ephemeral tokens by passing `apiKey: token.name`; the SDK detects the `auth_tokens/` prefix and switches to `BidiGenerateContentConstrained?access_token=` (logs an "experimental" warning). Vertex mode adds bearer headers, which browsers cannot set on WS, so Vertex needs a proxy.
- Raw WebSocket is fully feasible and is what Google's own example does: text JSON frames only, base64 blobs, one union field per frame, wait for `setupComplete`, handle `goAway` and reconnect with the handle. Close codes: normal 1000/1001 plus policy 1008 on Vertex without billing. Nothing requires the SDK.

## 11. Gotchas

- All binary is base64 inside JSON; a 20 ms chunk at 16 kHz is 640 bytes raw, ~856 bytes base64 plus envelope. Output is 24 kHz even though input is 16 kHz; resample mic input (44.1/48 kHz) client-side.
- `mimeType` on input must carry the rate: `audio/pcm;rate=16000`. Server `inlineData.mimeType` for audio out is not documented (UNVERIFIED value).
- `responseModalities` accepts exactly one entry and native audio models reject `TEXT`; text comes from `outputAudioTranscription`. Vertex docs still show `["audio", "text"]` for transcription (Vertex 2.5 GA behaviour, do not rely on it).
- 3.1 changed protocol semantics without a version bump: multiple parts per `serverContent` event, `clientContent` restricted to seeding behind `historyConfig`, `realtimeInput.text` for chat, turn coverage includes all video, sync-only tools, no affective/proactive, `thinkingLevel` (default `minimal`) replaces `thinkingBudget`; higher thinking levels add latency before first audio.
- Half-cascade vs native audio: no choice left on the Gemini API; native audio gives more natural prosody and emotion, at the cost of audio-only output and preview status. Vertex's GA `gemini-live-2.5-flash-native-audio` reports thinking as "Not supported".
- Preview churn: since mid-2025 the ids went `gemini-live-2.5-flash-preview` -> `gemini-2.5-flash-preview-native-audio-dialog` -> `...native-audio-preview-09-2025` -> `...12-2025` -> `gemini-3.1-flash-live-preview`; Vertex uses a different naming scheme (`gemini-live-2.5-flash-native-audio`). Make the model id a plain config string.
- Session and connection are different lifetimes: 10 min WS vs 15 min token budget vs unlimited with compression; design the adapter around resumption from day one.
- `sessionResumptionUpdate` can carry `resumable: false` with empty `newHandle`; never overwrite a stored handle with an empty one.
- `clientContent` always interrupts generation; `realtimeInput` never does on its own (VAD does).
- Seeding `history` sends `clientContent { turnComplete: true }`, which is also how a client asks for an answer, but it does **not** make the model take a turn. Measured 2026-09-13 against `gemini-3.1-flash-live-preview`: a session opened with two seeded turns and then left alone emitted no events at all for 15 seconds. So the seed primes the conversation only, and `turnComplete: false` is not needed.
- `goAway.timeLeft` is a proto Duration string (`"60s"`-style), not a number.
- The key rides on the socket URL here, and a rejected upgrade can put that URL in the error. Measured 2026-09-13 against a local server answering `403` to the upgrade, key in the query: **Bun 1.3.14 leaks it** (`ErrorEvent.message` is `WebSocket connection to '<full url>' failed: Connection ended`); **Node 24.16 does not** (`message` is `""`, the undici stack carries no URL); **Deno does not** (`NetworkError: failed to connect to WebSocket: Invalid status code: 403`). On all three, `message` is a **prototype getter**, not an own property, so `Object.keys` and any structural schema decode see nothing, and `String(event)` is `"[object ErrorEvent]"`. Only Deno names the status, so an upgrade rejected with 401/403 is detectable there alone.
- Ephemeral-token endpoint version disagreement (`v1beta` docs vs `v1alpha` SDK/example).
- Rate limits for Live are not published for the Gemini API; expect TPM-based throttling and 429s rather than a concurrent-session error.

## 12. Vertex AI parity

Vertex ("Gemini Enterprise Agent Platform") exposes the same `BidiGenerateContent` message schema on `wss://{location}-aiplatform.googleapis.com/ws/google.cloud.aiplatform.v1.LlmBidiService/BidiGenerateContent` with OAuth bearer headers and full model resource names; its docs use snake_case in examples (proto JSON accepts both casings) and the SDK's Vertex converter skips blob transformation and adds `explicitVadSignal`.
Model lineup differs: GA `gemini-live-2.5-flash-native-audio` (retires 2026-12-13, 1,000 concurrent sessions, 4M TPM, thinking unsupported) plus `gemini-3.5-transcribe-live-preview`; `gemini-3.1-flash-live-preview` is not listed on Vertex as of today.
Vertex adds `sessionResumption.transparent`, mid-session system-instruction updates via `role: "system"` clientContent, a 24 h resumption claim, Provisioned Throughput, regional endpoints and enterprise controls (CMEK, VPC-SC, data residency); ephemeral tokens are Gemini API only.
