## 3. Transports, auth, limits

| Transport | Endpoint                                                                                   | Auth                                                                                                    | Where                | Notes                                                                                                                                                                                                                                                                                                                                                                                             |
| --------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| WebSocket | `wss://api.openai.com/v1/realtime?model=<id>`                                              | `Authorization: Bearer <API key>` header, optional `OpenAI-Safety-Identifier`. No `OpenAI-Beta` header. | Server               | Also `?call_id=<id>` (no model) to attach a sideband socket to a WebRTC/SIP call. Browser use via subprotocols `realtime`, `openai-insecure-api-key.<ephemeral or key>`, optional `openai-organization.<org>`, `openai-project.<proj>` (voice-websockets.md).                                                                                                                                     |
| WebRTC    | `POST https://api.openai.com/v1/realtime/calls`                                            | Ephemeral `ek_...` from `POST /v1/realtime/client_secrets` (browser) or API key (server)                | Browser (and server) | With ephemeral key: body is the SDP offer, `Content-Type: application/sdp`; response body is the SDP answer. With API key: multipart form fields `sdp` and `session` (JSON). Data channel `oai-events` carries the same JSON events; audio on media tracks. Audio format negotiated in SDP, omit `audio.format`. `call_id` is returned in the `Location` response header (server-controls guide). |
| SIP       | trunk to `sip:<PROJECT_ID>@sip.api.openai.com;transport=tls` (EU: `sip-eu.api.openai.com`) | webhook + API key                                                                                       | Server               | Inbound only (outbound not supported). See section 9.                                                                                                                                                                                                                                                                                                                                             |

- Ephemeral keys: `POST /v1/realtime/client_secrets` with `{ expires_after: { anchor: "created_at", seconds: 10..7200 (default 600) }, session: <realtime or transcription session config> }` returns `{ value: "ek_...", expires_at: <unix>, session }`. The `session` sent here becomes the session defaults, so the browser need not send `session.update`.
- Older `POST /v1/realtime/sessions` and `/v1/realtime/transcription_sessions` still appear in reference nav but the guide only uses `client_secrets` (treat sessions endpoints as legacy; UNVERIFIED whether they will be removed).
- Max session duration: 60 minutes (realtime-conversations.md, Developer-notes blog "increased from 30"). Track `session.expires_at` from `session.created`. On expiry the server sends `error` with `code: "session_expired"` (community reports, UNVERIFIED wording). No documented idle disconnect timeout (UNVERIFIED). WebSocket close codes are not documented; community reports 1000 after `session.update` errors and 1006 abnormal closes (UNVERIFIED).
- No resumption after disconnect: a new socket is a new session; the client must re-inject history (community threads; no primary-source resume mechanism exists, verified absent from client events).
- Per-event limit: `input_audio_buffer.append` payload up to 15 MiB; PCM chunks must have even byte length.
- Context budget on 32k models: 4,096 max output, so ~28k for history; instructions + tools capped at 16,384 tokens (Developer-notes blog).

## 6. Turn-taking, interruption, tools

- VAD mode (default): server emits `speech_started`, `speech_stopped`, commits, creates the user item, and (if `create_response`) starts a response. On barge-in with `interrupt_response: true` the in-progress response is cancelled server-side (`response.done` status `cancelled`, reason `turn_detected`). WebRTC/SIP: server also clears its output buffer and truncates the item automatically. WebSocket: the client owns playback, must stop playback on `speech_started` and send `conversation.item.truncate` with the played `audio_end_ms` so unheard transcript is removed from context.
- Manual mode (`turn_detection: null`): `input_audio_buffer.append`* -> `input_audio_buffer.commit` -> `response.create`. `create_response: false` with VAD gives "VAD without auto response" (moderation hook), then client sends `response.create`.
- Text mid-session: `conversation.item.create` `{type:"message", role:"user", content:[{type:"input_text", text}]}` then `response.create`. System messages can be inserted the same way (`role: "system"`).
- Function calls: model emits `response.output_item.added` with `function_call` item, streams `response.function_call_arguments.delta`, ends with `.done` (`call_id`, `arguments` JSON string), then `response.done`. Client sends `conversation.item.create` `{type:"function_call_output", call_id, output: <string>}` and then `response.create`. Tools live at session level or per `response.tools`.
- Built-in MCP (realtime-mcp.md, SDK): tool `{type:"mcp", server_label, server_url | connector_id (connector_dropbox, connector_gmail, connector_googlecalendar, connector_googledrive, connector_microsoftteams, connector_outlookcalendar, connector_outlookemail, connector_sharepoint) | tunnel_id, authorization?, headers?, allowed_tools? (names or {tool_names, read_only}), require_approval: "always"|"never"|{always,never}, server_description?, allowed_callers?, defer_loading?}`. Server lists tools (`mcp_list_tools.*`), executes calls itself (`response.mcp_call.*`, output item `mcp_call`). With approval: item `mcp_approval_request` arrives; client answers `conversation.item.create` `{type:"mcp_approval_response", approval_request_id, approve, reason?}` then `response.create`. After a label is defined, later requests can reference it by `server_label` alone. Remote servers do not receive conversation context.
- Out-of-band: `response.create` with `conversation: "none"`, optional `metadata` to correlate, `output_modalities: ["text"]`, `input: [{type:"item_reference", id}, ...]` for custom context. Result is not added to the conversation. Always check `response.metadata` on `response.done`.

## 7. Conversation state

- Items have server ids (`item_...`, `resp_...`); `conversation.item.create` accepts a client `id` (SDK: string, 32 chars max UNVERIFIED). `retrieve` returns audio + transcript for a user audio item. `delete` removes from context (cache-busting).
- History injection: send `conversation.item.create` per item before the first `response.create`; assistant audio cannot be injected (text-only assistant items). Insert at start with `previous_item_id: "root"`.
- Truncation: `auto` drops from the oldest items when input exceeds the window (which busts the prompt cache); `retention_ratio` variant drops a bigger block once; `disabled` returns an error instead. GA service "automatically drops some audio tokens when a transcript is available" (Developer-notes blog).
- No conversation length limit besides context; session hard limit 60 min. No resume: reconnect = new session + replay history (verified: no client event exists for resume).

## 8. Transcripts

- Input: `audio.input.transcription.model` union in section 4; deltas as `conversation.item.input_audio_transcription.delta` (`item_id`, `content_index`, `delta`), final `...completed` (`transcript`, `usage`, `languages?`), failure `...failed`, diarized `...segment`. Legacy `whisper-1`/`gpt-4o-*` shut down 2027-02-26; prefer `gpt-live-transcribe` (streaming) or `gpt-transcribe` (post-commit, language detection). Logprobs via `include`.
- Output: `response.output_audio_transcript.delta`/`.done` alongside audio; text-only responses use `response.output_text.delta`. Transcript is generated by the speech model itself (not a separate ASR).
- Standalone transcription session: `type: "transcription"` over the same socket. `?intent=transcription` is STILL REQUIRED (verified live 2026-09-12: without `intent` or `model` on the URL the GA server closes the socket with `missing_model`). `gpt-live-transcribe` rejects `audio.input.turn_detection` with `invalid_value` "Turn detection is not supported for this transcription model" (verified live 2026-09-12); omit the field for it. Models `gpt-live-transcribe`, `gpt-transcribe`, `gpt-realtime-whisper`, `delay` knob, `turn_detection` or manual commit.

## 9. Image, video, SIP, GPT-Live, SDKs

- Image input: all `gpt-realtime*` models accept `{type:"input_image", image_url:"data:image/png;base64,..."}` inside a user message via `conversation.item.create`; billed as image tokens ($5/1M on 2.1). `detail` levels and size limits not documented for Realtime (UNVERIFIED). Video input: not supported (`gpt-live-1` page lists video as unsupported; no realtime model lists it).
- SIP (voice-sip): trunk -> `sip:<PROJECT_ID>@sip.api.openai.com;transport=tls` (TCP/TLS 5061, SRTP to 13.79.45.80/28, 23.98.140.64/28, 40.67.149.176/28, 40.83.204.240/28). Webhook `realtime.call.incoming` `{call_id, sip_headers: [From, To, Call-ID]}` signed with `webhook-id`/`webhook-timestamp`/`webhook-signature`. Verbs: `POST /v1/realtime/calls/{call_id}/accept` (body = realtime session config incl. model), `/reject` (`status_code`, default 603), `/refer` (`target_uri` like `tel:+1...` or `sip:...`), `/hangup`. Then attach `wss://api.openai.com/v1/realtime?call_id=...` with API key to observe and steer. DTMF arrives as `input_audio_buffer.dtmf_event_received`. Outbound SIP not supported.
- Sideband for WebRTC: `call_id` from `Location` header of the `/v1/realtime/calls` response, then the same `?call_id=` socket. Note: the `voice-server-controls?api=realtime` page currently renders GPT-Live sideband content (`session.instructions.append`, `session.thinking.append`, `session.input_audio.mute`, `response.item.create`, `session.close`); those event names are Live API, NOT Realtime API.
- GPT-Live (`gpt-live-1`, GA 2026-09-10): separate full-duplex product. `wss://api.openai.com/v1/live/sessions` (no query params) or `POST /v1/live/sessions` with `{session, transport:{type:"webrtc", sdp}}`; first event `session.start`, audio via `session.input_audio.append` / `session.output_audio.delta`, lifecycle `session.started` / `session.close` / `session.closed`; reasoning and tools delegated to a backend Responses model ("Responses delegation") or to the client ("client delegation"); 12 voices (Quartz, Ripple, Vesper, Willow, Stone, Gleam, Meridian, Bossa, Tempo, Beacon, Delta, Cinder); $0.05/min. Not covered further here.
- Translation (`/v1/realtime/translations`): own event vocabulary (`session.output_audio.delta`, `session.output_transcript.delta`, `session.input_transcript.delta`, `session.close`/`closed`), `audio.output.language`, one session per target language.
- SDK: `@openai/agents-realtime` `RealtimeAgent`/`RealtimeSession` exists (openai.github.io/openai-agents-js/guides/voice-agents/build/); another agent covers it.

## 10. Gotchas

- Audio is base64 inside JSON frames on WebSocket; default `audio/pcm` 24 kHz mono 16-bit LE; G.711 is 8 kHz; keep chunks small (~100 ms recommended by Azure docs) and even-length.
- No `OpenAI-Beta: realtime=v1` header on GA; sending it fails since 2026-05-12.
- Event renames beta -> GA: `response.audio.delta` -> `response.output_audio.delta`, `response.audio_transcript.delta` -> `response.output_audio_transcript.delta`, `response.text.delta` -> `response.output_text.delta`; `modalities` -> `output_modalities`; `input_audio_format`/`output_audio_format`/`voice`/`input_audio_transcription`/`turn_detection`/`input_audio_noise_reduction` moved under `audio.input.*` / `audio.output.*`; `max_response_output_tokens` -> `max_output_tokens`; `temperature` removed from the GA session schema. SDK class names still say `ResponseAudioDeltaEvent` etc., only the `type` literal changed.
- `output_modalities` accepts exactly `["audio"]` or `["text"]`, not both.
- `voice` locks after first audio output; `speed` only between turns; `model` never changes.
- 60-minute hard session limit; `session.created.session.expires_at` tells you when. Plan a hand-over (new session + replayed history) before that.
- `rate_limits.updated` arrives at every response start with reserved output tokens; the numbers move after completion.
- Truncating context busts prompt caching; prefer `retention_ratio` or manual `conversation.item.delete` of old items rather than per-turn `auto` trimming.
- `input_audio_buffer.append` gets no ack; only `commit`/VAD produce events. Manual `commit` on an empty buffer errors.
- `gpt-realtime` and `gpt-realtime-mini` (the 2025 GA ids) are already on the deprecation list (shutdown 2027-01-20); default new code to `gpt-realtime-2.1` / `gpt-realtime-2.1-mini`.
- `parallel_tool_calls` and `reasoning` are 2.x-only; 1.x models ignore or reject them (rejection behaviour UNVERIFIED).

## 11. Azure parity

- Azure OpenAI (Foundry): `wss://<resource>.openai.azure.com/openai/v1/realtime?model=<deployment-name>` (GA `/openai/v1`, no `api-version`), auth `api-key` header or `Authorization: Bearer <Entra token>` (scope `https://ai.azure.com/.default`); reference page states it "follows the OpenAI Realtime API specification" with one deviation: `audio.input.transcription.model` takes a deployment name. Models: gpt-realtime, -mini, -1.5, -2 (2026-05-07), -translate, -whisper, gpt-live-transcribe; `gpt-realtime-2.1` not yet listed; SIP and WebRTC endpoints differ (region-specific); 60-minute limit; Azure how-to examples still show beta field names (`modalities`, `input_audio_format`), treat as stale.
- Azure Voice Live: `wss://<resource>.services.ai.azure.com/voice-live/realtime?api-version=2026-04-10&model=...`; "mostly" the same events plus additive session fields (`azure_semantic_vad`, `azure_semantic_vad_multilingual`, `input_audio_noise_reduction: azure_deep_noise_suppression`, `input_audio_echo_cancellation`, `input_audio_sampling_rate`, Azure `voice` objects, avatar/viseme/timestamp events, `remove_filler_words`, `auto_truncate`); it fronts non-realtime models (GPT-5.x, 4.1) with Azure STT/TTS.
- Both Azure surfaces reject nothing extra on the wire that OpenAI GA accepts, so a shared codec with a pluggable URL builder and auth header is enough for parity; Voice Live extras should stay provider-typed.

## Appendix: reference WebSocket sequence (VAD mode, function call, barge-in)

```
C  connect wss://api.openai.com/v1/realtime?model=gpt-realtime-2.1  (Authorization: Bearer ...)
S  session.created            { session: { id, expires_at, ... } }
C  session.update             { session: { type: "realtime", instructions, audio: { input: { transcription: { model: "gpt-live-transcribe" }, turn_detection: { type: "semantic_vad", eagerness: "auto" } }, output: { voice: "marin" } }, tools: [...] } }
S  session.updated
C  conversation.item.create   { item: { type: "message", role: "user", content: [{ type: "input_text", text: "..." }] } }   (optional history)
S  conversation.item.created
C  input_audio_buffer.append  { audio: <base64 pcm16 24k> }   (repeat, no ack)
S  input_audio_buffer.speech_started        { audio_start_ms, item_id }
S  input_audio_buffer.speech_stopped        { audio_end_ms, item_id }
S  input_audio_buffer.committed             { item_id, previous_item_id }
S  conversation.item.created                { item: { type: "message", role: "user", content: [{ type: "input_audio" }] } }
S  conversation.item.input_audio_transcription.delta / .completed   (async, may land after response starts)
S  response.created                         { response: { id, status: "in_progress" } }
S  rate_limits.updated
S  response.output_item.added               { item: { type: "function_call", call_id, name } }
S  response.function_call_arguments.delta*  -> response.function_call_arguments.done { call_id, arguments }
S  response.output_item.done
S  response.done                            { response: { status: "completed", usage } }
C  conversation.item.create   { item: { type: "function_call_output", call_id, output: "{...}" } }
C  response.create            {}
S  response.created -> response.output_item.added { item: { type: "message", role: "assistant" } }
S  response.content_part.added              { part: { type: "audio" } }
S  response.output_audio.delta* interleaved with response.output_audio_transcript.delta*
S  input_audio_buffer.speech_started        (barge-in: client stops playback now)
S  response.done                            { response: { status: "cancelled", status_details: { reason: "turn_detected" } } }
C  conversation.item.truncate { item_id, content_index: 0, audio_end_ms: <played ms> }
S  conversation.item.truncated
...  next user turn continues as above
```
