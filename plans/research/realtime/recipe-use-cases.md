## 2. Browser and transport reality

OpenAI transports (Azure mirror table): WebRTC for client apps (~100 ms), WebSocket server-to-server (~200 ms), SIP for telephony. openai-realtime-console: WebSockets on the client are "not recommended in browsers". Ephemeral keys: `POST /v1/realtime/client_secrets`. WebRTC uses Opus and browser AEC/NS (webrtcHacks); the app never touches PCM.

OpenAI sideband (server-side controls): the WebRTC answer carries a `call_id` in the `Location` header; the server opens `wss://api.openai.com/v1/realtime?call_id=...` and can `session.update`, run tools, return `function_call_output`, observe events. Gotcha dated 2026-09-09 (community thread): "the sideband must use the same key that created the call"; calls created with ephemeral keys returned `call_id_not_found` on the sideband. The official `realtime-server-controlled` example (2026-08-27) uses the "unified interface": the server relays the browser's SDP to `POST /v1/realtime/calls` with the API key and then opens the sideband with the same key. So the hybrid is "server owns signalling and control, browser owns media", not "browser mints and connects alone".

Gemini transports: WebSocket only. Docs: "client-to-server generally offers better performance" and should use ephemeral tokens (`auth_tokens.create`, `uses`, `expireTime`, `newSessionExpireTime`, `liveConnectConstraints` to pin model and config); server-to-server uses the API key. There is no sideband: a browser-direct Gemini session must run tools in the browser or via an app-level channel. UNVERIFIED that no server-attach exists; none is documented.

Audio formats:

- OpenAI: pcm16 mono 24 kHz LE in and out (Azure troubleshooting: "Sample rate: 24kHz"); telephony formats g711 u-law / a-law at 8 kHz (Twilio GPT-Live tutorial sets the OpenAI side to Twilio's native "8kHz mu-law"). GA field names `session.audio.input.format` / `audio/pcm|pcmu|pcma` come from search snippets only: UNVERIFIED.
- Gemini: input "raw 16-bit PCM audio, 16kHz, little-endian", output 24 kHz. Best practices: "resamples microphone input (often 44.1kHz or 48kHz) to 16kHz before transmission", send 20 to 100 ms chunks, never buffer ~1 s.
- Existing client already covers this: `mic-worklet.ts` resamples `ctx.sampleRate` to `cfg.micSampleRate` from `/config` (16 kHz elevenlabs/mistral, 24 kHz in streaming-transcription for OpenAI), `playback-worklet.ts` is a ring buffer flushed on `assistant-cancelled`. For realtime both providers play back at 24 kHz, so `playbackSampleRate` becomes a constant and only `micSampleRate` varies (24 kHz OpenAI, 16 kHz Gemini).

Barge-in on a server relay:

- OpenAI WebSocket: on `input_audio_buffer.speech_started` stop playback, then send `conversation.item.truncate {item_id, content_index, audio_end_ms}`; "Truncating audio deletes the server-side text transcript" so the context matches what was heard. The server does this automatically only on WebRTC/SIP. Played-ms source: voice-loop's paced send (`chunkDurationMs` sleep per chunk) already tracks "ms handed to the speaker" server-side; that number minus the browser's ring-buffer depth is a good enough `audio_end_ms`. A more exact variant has the browser echo played-frame counts back on the WS.
- Gemini: server sends `serverContent.interrupted: true`; "You must immediately discard your client-side audio buffer". No truncate call. Same `assistant-cancelled` flush message as voice-loop.
- Also relevant: OpenAI `turn_detection: {type: "server_vad"|"semantic_vad"|null}`, `create_response:false` for moderation gating, `idle_timeout_ms` ("Are you still there?"); Gemini `automaticActivityDetection` with `startOfSpeechSensitivity`, `endOfSpeechSensitivity`, `prefixPaddingMs`, `silenceDurationMs` (500 to 800 ms recommended).

Echo cancellation: over a relay the browser's `getUserMedia` AEC is the only thing stopping the model from hearing its own voice through server VAD. voice-loop calls `getUserMedia({ audio: true })` (browser defaults, AEC on in Chrome/Firefox but not pinned); the realtime client should pass `{echoCancellation: true, noiseSuppression: true, autoGainControl: true}` explicitly. Gemini best practices do not cover AEC; webrtcHacks notes WebRTC ships "basic noise suppression by default".

Relay wire protocol for the realtime recipes (extends voice-loop's, so the client is shared):

```
[Browser]  getUserMedia({echoCancellation:true}) -> mic worklet (resample to micSampleRate) -> WS binary
   |  WS text: {type:"text", text}            (typed message injected as a user item)
   |  WS text: {type:"frame", jpegBase64}     (camera-assistant only, <= 1 fps)
   |  WS text: {type:"approve"|"deny", id}    (voice-tool-approval only)
[Server]  RealtimeSession per connection:
   Queue<RealtimeInput>  <- audio | text | frame | control
   Stream<RealtimeEvent> -> audio chunk (24 kHz s16le, binary frame, paced send)
                         -> user-transcript / assistant-transcript deltas (StatusEvent JSON)
                         -> tool-call / tool-result (StatusEvent JSON; Toolkit runs server-side)
                         -> interrupted (send assistant-cancelled; OpenAI also truncate with played ms)
                         -> turn boundaries (assistant-done)
[Browser]  ring-buffer playback worklet, flushed on assistant-cancelled
```

Differences from voice-loop that the shared client must absorb: `playbackSampleRate` is fixed at 24 kHz for both providers; `micSampleRate` is 24 kHz (OpenAI) or 16 kHz (Gemini) via `/config`; there is no `user-partial` event on Gemini unless `input_audio_transcription` is enabled, and OpenAI input transcripts arrive after the turn, not during it, so the UI shows the user's line late. The stop-word watcher disappears: barge-in is the provider's job.

Topology verdict: server relay (browser -> our WS -> Effect server -> provider WS). Reasons: it is the shape of every existing browser recipe (voice-loop, streaming-transcription, streaming-synthesis), it is the only shape both providers share, the `RealtimeSession` service is exercised end to end (browser-direct bypasses the library for the whole audio path), and the same server code accepts a WAV, a TTS persona, or Twilio frames as the input stream, which is what keeps recipes runnable without a mic. Cost is one hop (~100 ms extra per the Azure table) and owning truncate bookkeeping. Hybrid (server-relayed SDP + sideband) is an OpenAI-only follow-up: it is the right production topology for OpenAI browser apps but teaches transport plumbing, not composition, and has no Gemini analogue.

## 3. Inputs that make a recipe runnable without a mic

- WAV file as the user: strip the RIFF header, resample to the provider's input rate, pace chunks at real time (voice-loop's `chunkDurationMs` sleep), append trailing silence so server VAD commits the turn. Deterministic variant: OpenAI `turn_detection: null` + `input_audio_buffer.commit` + `response.create` ("push-to-talk"); Gemini disables `automaticActivityDetection` and sends explicit activity markers (exact `activityStart`/`activityEnd` field names UNVERIFIED). Gemini's own `command-line translation` example streams a remote audio URL into the model, so file-in is a vendor-blessed pattern.
- TTS persona as the caller: a text LanguageModel plays a scripted persona, `SpeechSynthesizer.streamSynthesisFrom` turns each line into PCM, the PCM feeds the session; the agent's output transcript feeds back to the persona model. Eval vendors (Coval, Hamming, Cekura per search snippets, UNVERIFIED primary) sell exactly this "synthetic caller across scenarios". OpenAI reports placeholder responses were "evaluated and tuned in experiments". No official cookbook does a full persona loop; this is a genuine gap a recipe can fill.
- Telephony as an optional runner: Twilio Media Streams messages `connected`, `start`, `media` (base64 `audio/x-mulaw` 8000 Hz mono), `dtmf`, `stop`, `mark` ("be notified when the audio that you have sent has been completed"), `clear` ("empties all buffered audio" on interruption). OpenAI accepts g711 natively so the relay only base64-wraps; Gemini needs mulaw <-> pcm16 16k/24k transcoding (Pipecat issue #1823 in search results). OpenAI SIP never puts media through our process (webhook + REST accept + sideband WS only), so a SIP runner exercises control, not the audio path. Both need a public URL, an account and a number: not local-runnable, so telephony stays an appendix, not a recipe.

## 4. Proposed recipes

1. `realtime-voice-agent` (accept, first). Idea: one duplex session where the model owns turn-taking and tool calls interleave with speech. Features: server VAD, barge-in (OpenAI `conversation.item.truncate` from paced-send bookkeeping; Gemini `interrupted`), function tools from a `Toolkit` (so the `mcp-tools` toolkit plugs in unchanged), input/output transcripts, text injection. Mirrors voice-loop file for file: same `client/` (mic worklet, ring-buffer playback, `StatusEvent` JSON + binary frames), same `wsHandler` bridge, `--provider openai|google`. Evidence: openai-realtime-console, Gemini command-line examples, chatSupervisor. UI: voice-loop's page plus a tool-call line. Runs on Bun/Node/Deno through `serveRecipe`, no new platform needs.
2. `voice-tool-approval` (accept). Idea: a sensitive tool call is gated by a human while the call stays live; the model keeps talking ("I'm still waiting on that") until the approval resolves. Features: function tools, async tool result (OpenAI placeholder responses; Gemini `NON_BLOCKING` + `scheduling`), text injection of the verdict, OpenAI MCP `mcp_approval_request` as the hosted variant. Mirrors `tool-call-approval` (gate before `run`, still one result per call) plus `sleeper-agent` (a `Deferred` the turn awaits). Evidence: OpenAI voice-agents guide "Guardrails and human review when spoken workflows need safety checks or approvals", realtime-mcp approval items. UI: voice-agent page plus Approve/Deny buttons; approval is a button, not a spoken "yes", to avoid an identity-sensitive path. Runs anywhere the first recipe runs.
3. `simulated-caller` (accept). Idea: the user is just a `Stream<Uint8Array>`; swap the mic for a WAV or a TTS persona and the same session becomes a test harness that prints per-turn latency (speech end to first audio byte) and writes both sides' audio to `output/`. Features: manual turn mode for determinism, transcripts, metrics as stream operators. Mirrors `basic-metrics` and voice-loop's pacing; no browser. Evidence: eval-vendor synthetic callers (UNVERIFIED primary), OpenAI's own eval remarks, Gemini file-in example. `--stack realtime|pipeline` runs the same WAV through voice-loop's pipeline, which absorbs the `realtime-vs-pipeline` comparison as a flag. Runs headless on all three runtimes; CI-friendly with a checked-in WAV.
4. `camera-assistant` (accept, Gemini only). Idea: a second modality on the same session; frames are just another input variant in the `Queue<RealtimeInput>`. Features: video at 1 fps JPEG, `mediaResolution`, `contextWindowCompression` (mandatory: audio+video caps at 2 min), `GoAway` handling. Mirrors `realtime-voice-agent` plus `multimodal-embedding`'s "one space, two modalities" framing. Evidence: live-api-web-console, Pipecat vision bot, Gemini app camera/screen share. UI: `<video>` preview + canvas snapshot timer; `--source camera|screen` flips `getUserMedia` to `getDisplayMedia`, which covers the screen-share copilot without a second recipe. Headless fallback: `--frames dir/` of JPEGs paced at 1 fps.
5. `call-supervisor` (accept, smallest). Idea: a second consumer of the shared event stream classifies the live conversation without touching it. Generic path: `Stream.share` the transcript events, run a text `LanguageModel` classifier (intent, frustration, "wants a human") and surface a badge; OpenAI-native path: `response.create` with `conversation:"none"`, `metadata`, `output_modalities:["text"]` so the same session does the classification. Mirrors voice-loop's `Stream.share` + watcher fibre and `streaming-tool-output` (side channel to the UI). Evidence: OpenAI out-of-band docs and cookbook, `create_response:false` moderation gating, retail escalation agent. UI: voice-agent page plus a status badge. Runs anywhere; Gemini uses the generic path only.

What the five share, and what `recipe-kit` needs: nothing new at the platform layer (all five use `serveRecipe` or `runRecipe`, `bundleClient`, `argv`, `output`). A shared `_shared/realtime.ts` alongside `_shared/model.ts` should own the `--provider openai|google` layer choice and the per-provider mic rate, the same way `layersFor` does in voice-loop. The `client/` directory of `realtime-voice-agent` is copied by recipes 2, 4 and 5 with one extra control each, matching how voice-loop copied streaming-transcription's client instead of sharing a package. Recipe 3 has no client. Suggested landing order: 1, 3 (the harness makes 2, 4, 5 testable in `recipe.test.ts` without a mic), then 2, 5, 4.

Feature coverage across the five (so nothing in the provider matrix is left untaught): server VAD and barge-in (1), function tools and MCP (1, 2), async tool results (2), text injection (1, 2), video and context compression (4), out-of-band responses (5), manual turn mode and metrics (3). Not covered on purpose: proactive audio, affective dialog, session resumption, SIP, ephemeral tokens; see the reject list.

## 5. Reject list

- `realtime-vs-pipeline`: a benchmark, not a composable idea; folded into `simulated-caller --stack`.
- `live-translator`: separate models and session types (`gemini-3.5-live-translate-preview`, `gpt-realtime-translate` on `/realtime/translations`), so it is a different service surface from `RealtimeSession`; as a `RealtimeSession` recipe it would be a system prompt, a thin wrapper.
- `phone-agent`: needs a Twilio account, a number and a public URL, so it is not locally runnable; OpenAI SIP keeps media out of our process entirely. Keep as an appendix in `simulated-caller` (mulaw adapter) and revisit for `recipes-extras`.
- `session-handoff`: Gemini-only lifecycle plumbing (`GoAway`, `sessionResumption.handle`); OpenAI has no resumption. Belongs inside the Gemini adapter as automatic reconnect, documented, not taught as a recipe.
- Screen-share copilot: one flag on `camera-assistant`.
- Drive-through / kiosk ordering: `realtime-voice-agent` with a menu prompt and cart tools; no new primitive (LiveKit `drive_thru` confirms it is tools + prompt).
- Voice data entry / form filling: tools plus structured output, already covered by `structured-output` and recipe 1.
- Meeting copilot with proactive audio: Gemini 2.5-only preview flag; recording a meeting is identity-sensitive; no cross-provider story.
- Human handoff / warm transfer: SIP `refer` and participant management are resource management on a telephony provider; rejected by the recipe rules.
- Accessibility reader: that is `streaming-synthesis`.
- Game NPC: no primitive beyond affective dialog, which is a config flag on recipe 1.
- Language tutor: personality prompt on recipe 1; pronunciation feedback would need per-word scoring no realtime API exposes (UNVERIFIED).
- Voice MCP agent: `mcp-tools` already builds the `Toolkit`; recipe 1 accepts it, so a separate recipe would duplicate.
- Browser-direct / hybrid sideband transport recipe: OpenAI-only, teaches transport plumbing, and the 2026-09-09 key-matching gotcha makes it brittle; document it in `docs/realtime` instead.
