# Plan: v0.13

Four items: reranking (#130), the RAG recipe (#131), image generation
(#133), and live audio (#132).

## Where we are

v0.12 shipped the compatibility substrate: the generic
`chat-completions` base, the `@effect-uai/openai` brand package, and
the gateway story. v0.13's first two slots closed on 2026-08-29:

- **#128 MCP client.** `@effect-uai/mcp` is written, tested, and
  documented; it needs its first manual publish and an OIDC trusted
  publisher on npm before the lockstep release can carry it.
- **#129 OpenRouter.** Shipped as gateway documentation over
  `@effect-uai/chat-completions` rather than a package. There is no
  `@effect-uai/openrouter` and there does not need to be.

So the substrate is done. v0.13 is now about capabilities, and the
capability matrix has one shape of hole: audio is covered end to end
(STT, TTS, music), text is covered end to end (LLM, embeddings,
search, read, sandboxes, browser), and there is no image story and no
duplex story at all.

## Scope note

The original sizing put three items in a release and named live audio
as _bigger than image generation_, which was itself deferred as a
v0.14 headliner. This plan takes four, two of which were each sized as
a headliner. That is a real risk, not a formality. The mitigation is
the sequencing below: the two cheap items land first and are
independently shippable, so if live audio runs long it slips to v0.14
without holding the release.

One thing that makes the scope less alarming than it reads: **v0.13
adds three capabilities and zero provider packages.** Capability
implementations land in packages that already exist; the one new
package is `@effect-uai/retrieval` (utilities, not a provider:
[plans/chunking.md](./chunking.md)).

## 1. Reranking (#130)

**Why first.** Lowest effort on the board, and it fixes a live bug:
[packages/providers/jina/package.json:4](../packages/providers/jina/package.json#L4)
advertises `rerank` in its description and keywords for something that
does not exist. That is published metadata promising a feature we
don't ship.

**Shape.** A `Reranker` service tag in core, following
`EmbeddingModel` exactly: a `Context.Service` under
`@betalyra/effect-uai/Reranker`, a `CommonRerankRequest` for the
cross-provider fields, module-level `rerank(request)` sugar that does
`Effect.flatMap(Reranker, …)`, and provider request types that extend
the common one to narrow `model` and add vendor knobs.

```ts
type CommonRerankRequest = {
  readonly query: string
  readonly documents: ReadonlyArray<string>
  readonly model: string
  readonly topN?: number
}

type RerankResult = {
  readonly index: number // position in the request's `documents`
  readonly score: number // higher is better; range deliberately unpromised
}
```

Researched ([plans/research/reranking.md](./research/reranking.md)):
the Cohere/Jina shape is the de-facto standard (vLLM and OpenRouter
both implement it), so one tag covers the field. No document echo in
the common response: Cohere v2 dropped it and the caller already holds
`documents`; `index` is enough. Results come back sorted descending;
core promises "higher is better" and nothing about score range or
calibration (Jina's listwise scores are candidate-set-dependent).

**Provider.** Jina only, as `JinaReranker.ts` alongside the existing
`JinaEmbedding.ts` / `JinaReader.ts`, exported at `./JinaReranker`,
copy-per-surface like the other two (there is no shared client to
reuse). Model union: `jina-reranker-v3.5` (July 2026 flagship,
default), `jina-reranker-v3`, `jina-reranker-m0`, open-union tail.
Mistral, OpenAI, and Gemini have no rerank endpoint to wrap, and
Google's Ranking API is GCP-gated; Cohere / Voyage / Mixedbread stay
docs candidates. A later cheap win: OpenRouter now proxies
Cohere-shaped `/rerank`, so one gateway adapter would reach Cohere and
Voyage without new provider packages.

**Resolved (was the open question).** `documents` is strings-only in
the common request; multimodal documents are a `jina-reranker-m0`
widening on `JinaRerankRequest`, the same way `sparse` /
`multivector` live on `JinaEncoding` rather than `EmbedEncoding`.
`instruction` also stays provider-typed (only Contextual has a real
field; Voyage takes instructions as query text).

**Docs framing.** Position `Reranker` as a per-hop candidate-filtering
primitive an agent loop reaches for, not as "step 2 of the RAG
pipeline"; the strategic research (GO, reshaped) is in the research
doc.

**Done when.** `Reranker` tag + Jina implementation + unit tests
against a mock; `docs/reranking/index.md` rewritten from "coming soon"
to usage; the jina `package.json` description and keywords are true.

## 2. RAG retrieval recipe (#131): `retrieve-and-rerank`

**Why.** Embeddings plus reranking is the complete retrieval story,
and the recipe is what makes that legible on one page. It is also the
first place the two capabilities are shown composing rather than
existing side by side.

**Positioning** (researched,
[research/rag-recipe.md](./research/rag-recipe.md)):
[recipes/basic-embedding/](../recipes/basic-embedding/) is already
"embed + rank by cosine" in one file, so this ships as a **new**
recipe, working name `retrieve-and-rerank`, whose story is the delta:
candidates by cosine, precision by `Reranker`, answer by `loop`. One
`JINA_API_KEY` covers both capabilities. `basic-embedding` stays the
embeddings teaching sample.

**Shape.** Retrieve a wide candidate set by cosine, rerank the
candidates with a cross-encoder, feed the top few to the model as
grounded context. Every piece already exists except the middle one:
`EmbeddingModel.embedMany` (with `task: "query"` / `task: "document"`
demonstrated correctly; asymmetry is still universal in
retrieval-tuned models), `Vector.cosine`
([packages/core/src/math/Vector.ts:50](../packages/core/src/math/Vector.ts#L50)),
then `Reranker.rerank`, then an ordinary `loop`.

Deliberately **no vector database.** An in-memory corpus keeps the
recipe about the retrieval shape rather than about wiring storage.
Recipes are type-checked and tested in CI; the database-backed
version is item 2b in `recipes-extras/`.

**Corpus and showcase (decided).** A curated inline `corpus.ts` of
30-50 short documents engineered with near-miss distractors: for each
demo query, the cosine top ranks contain topically-similar-but-wrong
documents (negation, constraints, exact identifiers) that the
reranker demotes. The terminal output is the showcase: two ranked
lists side by side, "by cosine" vs "after rerank", so the reranker's
value is visible without explanation. Deterministic, zero fetch,
CI-testable, and the corpus is the one obvious swap point for a
reader's own data.

**Convention.** Full current recipe shape (`recipe.ts`, `app.ts`,
`run-node.ts` / `run-bun.ts` / `run-deno.ts`, `recipe.test.ts`,
`README.md`), not the older flat `index.ts`.

**Done when.** The recipe runs against real Jina, passes tests against
mocks, appears in `docs/recipes/index.md`, the Astro sidebar, and the
landing-page recipe grid.

## 2b. Hybrid RAG recipe (#131, flagship)

The simple recipe (item 2) teaches the retrieval shape; this one is
the flagship: the full modern stack (hybrid retrieval, rank fusion,
cross-encoder rerank) on a single database file, no server.

**RRF lives in `@effect-uai/retrieval`** (decided; plan:
[plans/chunking.md](./chunking.md)). Reciprocal rank fusion
(`score(d) = Σ weight_i / (k + rank_i(d))`, k=60 default, the
industry-standard constant, optional per-ranking weights per current
practice in Elasticsearch / Qdrant v1.17 / Supabase) ships as the
`Rank` module of the new retrieval utilities package. It was first
implemented as `core/src/math/Rank.ts`; that file, its test, and the
core `./Rank` export move to the package before release (unpublished,
so the move is free). The retrieval package is therefore part of
v0.13: this recipe depends on it.

**BM25 explicitly stays out of core.** The formula is trivial but a
usable BM25 needs corpus state (inverted index, per-term document
frequencies, average doc length) plus tokenization, and tokenization
is where the quality lives (stemming, stopwords, unicode, CJK). A
naive lowercase-split BM25 in core is a toy; a good one is a search
engine. The recipe's database also already does it better: libsql
ships SQLite's FTS5 with the built-in `bm25()` ranking function, plus
native vector search (`F32_BLOB` columns, DiskANN via `vector_top_k`).
One on-file database provides both retrieval legs.

**The retrieval utilities package.** RRF's home is
`@effect-uai/retrieval` (chunking, `Rank.rrf`, in-memory BM25, HF
tokenizer layer; the `Tokenizer` tag itself goes in core). Full plan:
[plans/chunking.md](./chunking.md). `Vector` stays in core.

**Recipe shape.** `recipes-extras/hybrid-rag/` (extras is right: it
carries the native libsql dependency without adding it to the recipes
workspace):

**Corpus (decided).** One Project Gutenberg public-domain book (e.g.
The Adventures of Sherlock Holmes), fetched as a single plain-text
GET on first run and cached to a local file, Gutenberg header/footer
stripped. No auth, no dataset registry, one URL. Big enough that
chunking, both retrieval legs, and reranking all earn their place;
still one command to run. Queries are story questions where many
chunks mention the same characters but only one holds the answer.

1. Ingest: chunk (~512 tokens, 10-20% overlap, sentence boundaries;
   the 2026 benchmark-validated baseline), `embedMany`, insert into
   one libsql file (`file:rag.db`) with an `F32_BLOB` column and an
   FTS5 table.
2. Query leg A: `vector_top_k` dense KNN. Leg B: FTS5 `bm25()`.
   ~100 candidates per leg.
3. `Rank.rrf` (from `@effect-uai/retrieval`) fuses the two rankings.
4. `Reranker.rerank` (item 1) re-scores the fused top ~20.
5. Ordinary `loop` answers from the top ~5 as grounded context.

The depths (100/leg, rerank 20, answer from 5) are the citable 2026
production defaults, not arbitrary demo numbers.

**De-risked** ([research/rag-recipe.md](./research/rag-recipe.md)):
vector search and FTS5 `bm25()` were verified empirically in one
embedded `file:` database, in-process, on Node 24, Bun 1.3, and Deno
2.9 (`--allow-ffi`), so the recipe ships all three runners. Caveats to
encode: single-writer only (concurrent writers corrupt the vector
index shadow table); join `vector_top_k` on `rowid`; the web client
variant rejects `file:` URLs. Avoid `sqlite-vec` and the beta Turso
rewrite.

**SQL layer.** Use the standard Effect SQL pattern, not raw
`@libsql/client` calls: `@effect/sql-libsql@4.0.0-rc.111` (exactly our
effect pin) wraps `@libsql/client@^0.17.4` and exposes
`LibsqlClient.layer({ url: "file:rag.db" })` returning
`Layer<LibsqlClient | SqlClient>`. This doubles as a demo of
effect-uai composing with the wider Effect ecosystem.

**Positioning** (researched): no mainstream TS framework's canonical
RAG example does lexical+dense hybrid with rank fusion (Vercel AI SDK,
LangChain JS, LlamaIndex.TS are dense-only; Mastra's "hybrid" is
metadata filtering). This is the first that is zero-infra and still
architecturally what production teams deploy.

**Done when.** RRF in core with unit tests; the recipe ingests and
answers against a real libsql file end to end on all three runtimes;
extras README follows the user-POV docs convention.

## 3. Image generation (#133)

**Why.** The most conspicuous hole in the capability matrix. Audio has
three capabilities; images have none.

**Researched and designed 2026-09-04.** Full plan:
[plans/image-generation.md](./image-generation.md); research:
[plans/research/image-generation.md](./research/image-generation.md).
The paragraphs below are the summary; the plan wins on any conflict.

**Shape.** Two surfaces. (1) An `ImageGenerator` service tag with
separate `generate` and `edit` (the open question below is resolved
that way) and a marker-gated `streamGeneration` for OpenAI partials,
following the `Transcriber` / `SpeechSynthesizer` marker pattern.
Common request: prompt, reference images, aspect ratio, resolution
tier, `n`. Mask, quality, transparent background, search grounding
stay provider-typed. (2) Image output inside `LanguageModel` turns:
an `OutputImage` content block and two `TurnEvent`s, because Gemini
emits images as parts of the chat turn and OpenAI emits them through
the Responses `image_generation` built-in tool. That second surface
is what the conversational-edit recipe uses and is the slip
candidate.

The output reuses the existing `Media` / `Image` domain
([packages/core/src/domain/Image.ts](../packages/core/src/domain/Image.ts)),
already exported from core as `./Image` and `./Media`. Generated
images compose with multimodal language models with no glue, because
they are the same type the LM inputs already use.

**Providers.** OpenAI `gpt-image-2` via the Images API into
`@effect-uai/openai` (the original `gpt-image-1` target shuts down
2026-12-01), and Google Nano Banana 2 / Pro / Lite via
`generateContent` into `@effect-uai/google` (Imagen shut down on the
Gemini API 2026-08-17). The OpenAI adapter takes a base URL, which
reaches xAI, Meta, Requesty, and the Vercel AI Gateway as gateway
docs, the same move as OpenRouter over `chat-completions`. One new
package, `@effect-uai/fal`, is planned separately and trails into a
patch release; it covers Seedream, Qwen, Muse, and the FLUX fast tier.
BFL direct, OpenRouter, LoRA, image utilities, and real-time diffusion
are deferred.

**Recipes.** Two shipped: `storyboard` (structured output drives
multi-reference generation, with the critique-and-retry loop folded in
rather than split out) and `conversational-image-edit` (a REPL that
keeps its subject across edits). `ad-variant-matrix` was dropped:
generating variants in parallel is `Effect.forEach` with a concurrency
bound, which `multi-model-compare` and storyboard's cast stage already
demonstrate.

**Done when.** Tag + two providers + tests; `docs/image-generation/`
rewritten from "coming soon" with provider pages; the two surface-1
recipes. Surface 2 and its recipes ship with it if ready, otherwise in
v0.14.

## 4. Live audio (#132)

**Why last.** Largest by a distance, and the only item whose design is
genuinely unsettled. It is also the one whose value is clearest to
anyone evaluating the library.

**What it is not.** Not the voice loop. `Transcriber → LanguageModel →
SpeechSynthesizer` already ships and covers the common case
([recipes/voice-loop/](../recipes/voice-loop/)). This is the other
archetype: one long-lived duplex session where the model owns
turn-taking.

Four things a native session adds over the pipeline: model-native
barge-in via server-side VAD instead of client-side stop-words;
mid-utterance tool calls instead of atomic STT to LLM to TTS turns;
sub-200ms turn-taking by amortizing the per-boundary latency; and
camera-in streams.

**Shape.** A `RealtimeSession` service. Likely a session value carrying
a `Queue<RealtimeInput>` you push into (audio frames, video frames,
text, control) and a `Stream<RealtimeEvent>` you consume from (audio
chunks, transcript deltas, tool calls, turn boundaries). The right
backpressure, cancellation, and interrupt semantics get designed
alongside the first integration, not in advance.

**Providers.** OpenAI Realtime (`gpt-realtime`, WebSocket first;
WebRTC is a later transport) and Gemini Live. Do both, or the
abstraction is one provider's API with a tag on it.

**Prior art in-repo.** Seven WebSocket adapters already exist
(`openai/realtimeStt.ts`, `mistral/realtimeStt.ts`,
`elevenlabs/realtimeStt.ts` and `realtimeTts.ts`,
`inworld/realtimeStt.ts` and `realtimeTts.ts`, `browser/internal/cdp.ts`).
Two gotchas they all encode and this must too:

- `Socket.makeWebSocket` treats every close as an error. Pass
  `closeCodeIsError: (code) => code !== 1000 && code !== 1001 && code !== 1005`.
- Use `Queue<A, Cause.Done>` + `Queue.end` on reader fibers, never
  `Queue.shutdown`, which clears queued items and interrupts pending
  takes instead of letting consumers drain.

**Risk.** This is the slip candidate. If it isn't converging by the
time 1 through 3 are done, cut it to v0.14 and ship v0.13 as three
capabilities. Do not ship a `RealtimeSession` designed against one
provider to make a date.

**Done when.** Tag + both providers + a duplex recipe;
`docs/realtime/index.md` rewritten from "coming soon".

## Cross-cutting

**Landing page.** [Hero.astro:21](../webpage/src/components/Hero.astro#L21)
says 8 capabilities. Reranking, image generation, and live audio make 11. Provider count stays 14: no new provider packages. Recipe count
rises by one per new recipe. `CapabilitiesSection.tsx` needs a card per
new capability, and a new card icon must be registered in both
`RecipesSection.tsx` and `PageTitle.astro`'s `iconMap`.

**Docs.** Three "coming soon" pages get rewritten as usage docs:
`docs/reranking/`, `docs/image-generation/`, `docs/realtime/`. Each
already states the intended design, so they are the specification, not
a blank page. Written user-POV: the developer's problem, not the wire.

**Release mechanics.** `@effect-uai/mcp` is in the changeset fixed
group but unpublished. Its first manual publish and its npm OIDC
trusted publisher must both be done before the v0.13 lockstep release,
or the release workflow fails on that package. `@effect-uai/retrieval`
repeats the same dance: fixed group at the current group version,
first manual publish, then OIDC trusted publisher.
