# Plan: v0.13

Four items: reranking (#130), the RAG recipe (#131), image generation
(#133), and live audio (#132).

## Where we are

v0.12 shipped the compatibility substrate: the generic
`chat-completions` base, the `@effect-uai/openai` brand package, and
the gateway story. v0.13's first two slots closed on 2026-08-29:

- **#128 MCP client.** `@effect-uai/mcp` is written, tested, and
  documented; it needs its first manual publish and an OIDC trusted
  publisher on npm before the lockstep release can carry it.
- **#129 OpenRouter.** Shipped as gateway documentation over
  `@effect-uai/chat-completions` rather than a package. There is no
  `@effect-uai/openrouter` and there does not need to be.

So the substrate is done. v0.13 is now about capabilities, and the
capability matrix has one shape of hole: audio is covered end to end
(STT, TTS, music), text is covered end to end (LLM, embeddings,
search, read, sandboxes, browser), and there is no image story and no
duplex story at all.

## Scope note

The original sizing put three items in a release and named live audio
as _bigger than image generation_, which was itself deferred as a
v0.14 headliner. This plan takes four, two of which were each sized as
a headliner. That is a real risk, not a formality. The mitigation is
the sequencing below: the two cheap items land first and are
independently shippable, so if live audio runs long it slips to v0.14
without holding the release.

One thing that makes the scope less alarming than it reads: **v0.13
adds three capabilities and zero provider packages.** Every
implementation lands in a package that already exists.

## 1. Reranking (#130)

**Why first.** Lowest effort on the board, and it fixes a live bug:
[packages/providers/jina/package.json:4](../packages/providers/jina/package.json#L4)
advertises `rerank` in its description and keywords for something that
does not exist. That is published metadata promising a feature we
don't ship.

**Shape.** A `Reranker` service tag in core, following
`EmbeddingModel` exactly: a `Context.Service` under
`@betalyra/effect-uai/Reranker`, a `CommonRerankRequest` for the
cross-provider fields, module-level `rerank(request)` sugar that does
`Effect.flatMap(Reranker, …)`, and provider request types that extend
the common one to narrow `model` and add vendor knobs.

```ts
type CommonRerankRequest = {
  readonly query: string
  readonly documents: ReadonlyArray<string>
  readonly model: string
  readonly topN?: number
}

type RerankResult = {
  readonly index: number // position in the request's `documents`
  readonly score: number
  readonly document?: string // echoed only when the caller asks
}
```

The four candidate providers converge on
`POST /rerank { model, query, documents } → { results: [...] }`, so
one tag covers all of them.

**Provider.** Jina only, as `JinaReranker.ts` alongside the existing
`JinaEmbedding.ts` / `JinaReader.ts`, exported at `./JinaReranker`.
`jina-reranker-v3` and `jina-reranker-m0`. Cohere, Voyage, and
Mixedbread stay listed as candidates in the docs; adding them is a
later, mechanical follow-up, not v0.13.

**Open question.** Whether `documents` accepts structured input
(multimodal reranking, which `jina-reranker-m0` supports) or strings
only in v1. Recommendation: strings only. Multimodal reranking is a
Jina-specific widening and belongs on `JinaRerankRequest`, the same
way `sparse` / `multivector` encodings live on `JinaEncoding` rather
than the common `EmbedEncoding`.

**Done when.** `Reranker` tag + Jina implementation + unit tests
against a mock; `docs/reranking/index.md` rewritten from "coming soon"
to usage; the jina `package.json` description and keywords are true.

## 2. RAG retrieval recipe (#131)

**Why.** Embeddings plus reranking is the complete retrieval story,
and the recipe is what makes that legible on one page. It is also the
first place the two capabilities are shown composing rather than
existing side by side.

**Shape.** Retrieve a wide candidate set by cosine, rerank the
candidates with a cross-encoder, feed the top few to the model as
grounded context. Every piece already exists except the middle one:
`EmbeddingModel.embedMany`, `Vector.cosine`
([packages/core/src/math/Vector.ts:50](../packages/core/src/math/Vector.ts#L50)),
then `Reranker.rerank`, then an ordinary `loop`.

Deliberately **no vector database.** An in-memory corpus keeps the
recipe about the retrieval shape rather than about wiring pgvector or
Qdrant. Recipes are type-checked and tested in CI; a recipe needing
external infra belongs in `recipes-extras/`, and this one shouldn't
need to.

**Convention.** Full current recipe shape (`recipe.ts`, `app.ts`,
`run-node.ts` / `run-bun.ts` / `run-deno.ts`, `recipe.test.ts`,
`README.md`), not the older flat `index.ts`. Worth noting that
[recipes/basic-embedding/](../recipes/basic-embedding/) is currently
only `README.md` + `index.ts`, with no runner and no test. The RAG
recipe should not copy that.

**Done when.** The recipe runs against real Jina, passes tests against
mocks, appears in `docs/recipes/index.md`, the Astro sidebar, and the
landing-page recipe grid.

## 3. Image generation (#133)

**Why.** The most conspicuous hole in the capability matrix. Audio has
three capabilities; images have none.

**Shape.** An `ImageGenerator` service tag covering text-to-image,
image edit, and inpainting. One-shot, like embeddings: prompt in,
images out, no streaming. A few providers stream partial images; that
is not broadly supported and would complicate the core abstraction for
a minority feature.

The output reuses the existing `Media` / `Image` domain
([packages/core/src/domain/Image.ts](../packages/core/src/domain/Image.ts)),
already exported from core as `./Image` and `./Media`. That is the
whole reason this is M and not L: generated images compose with
multimodal language models with no glue, because they are the same
type the LM inputs already use.

**Providers.** OpenAI `gpt-image-1` into the existing
`@effect-uai/openai`, and Imagen via the Gemini API into the existing
`@effect-uai/google`. Both packages already exist and both already
have the HTTP plumbing. Black Forest Labs and Stability stay
candidates in the docs.

**Open question.** Whether edit and inpaint are separate methods
(`generate` / `edit`) or one method whose request optionally carries a
reference image and a mask. Recommendation: separate methods. The
required fields differ, and one method with three optional fields that
are conditionally required is exactly the shape that types poorly.

**Done when.** Tag + two providers + tests; `docs/image-generation/`
rewritten from "coming soon"; a recipe showing an image tool inside an
agent loop, which is the framing that distinguishes this from a thin
HTTP wrapper.

## 4. Live audio (#132)

**Why last.** Largest by a distance, and the only item whose design is
genuinely unsettled. It is also the one whose value is clearest to
anyone evaluating the library.

**What it is not.** Not the voice loop. `Transcriber → LanguageModel →
SpeechSynthesizer` already ships and covers the common case
([recipes/voice-loop/](../recipes/voice-loop/)). This is the other
archetype: one long-lived duplex session where the model owns
turn-taking.

Four things a native session adds over the pipeline: model-native
barge-in via server-side VAD instead of client-side stop-words;
mid-utterance tool calls instead of atomic STT to LLM to TTS turns;
sub-200ms turn-taking by amortizing the per-boundary latency; and
camera-in streams.

**Shape.** A `RealtimeSession` service. Likely a session value carrying
a `Queue<RealtimeInput>` you push into (audio frames, video frames,
text, control) and a `Stream<RealtimeEvent>` you consume from (audio
chunks, transcript deltas, tool calls, turn boundaries). The right
backpressure, cancellation, and interrupt semantics get designed
alongside the first integration, not in advance.

**Providers.** OpenAI Realtime (`gpt-realtime`, WebSocket first;
WebRTC is a later transport) and Gemini Live. Do both, or the
abstraction is one provider's API with a tag on it.

**Prior art in-repo.** Seven WebSocket adapters already exist
(`openai/realtimeStt.ts`, `mistral/realtimeStt.ts`,
`elevenlabs/realtimeStt.ts` and `realtimeTts.ts`,
`inworld/realtimeStt.ts` and `realtimeTts.ts`, `browser/internal/cdp.ts`).
Two gotchas they all encode and this must too:

- `Socket.makeWebSocket` treats every close as an error. Pass
  `closeCodeIsError: (code) => code !== 1000 && code !== 1001 && code !== 1005`.
- Use `Queue<A, Cause.Done>` + `Queue.end` on reader fibers, never
  `Queue.shutdown`, which clears queued items and interrupts pending
  takes instead of letting consumers drain.

**Risk.** This is the slip candidate. If it isn't converging by the
time 1 through 3 are done, cut it to v0.14 and ship v0.13 as three
capabilities. Do not ship a `RealtimeSession` designed against one
provider to make a date.

**Done when.** Tag + both providers + a duplex recipe;
`docs/realtime/index.md` rewritten from "coming soon".

## Cross-cutting

**Landing page.** [Hero.astro:21](../webpage/src/components/Hero.astro#L21)
says 8 capabilities. Reranking, image generation, and live audio make 11. Provider count stays 14: no new provider packages. Recipe count
rises by one per new recipe. `CapabilitiesSection.tsx` needs a card per
new capability, and a new card icon must be registered in both
`RecipesSection.tsx` and `PageTitle.astro`'s `iconMap`.

**Docs.** Three "coming soon" pages get rewritten as usage docs:
`docs/reranking/`, `docs/image-generation/`, `docs/realtime/`. Each
already states the intended design, so they are the specification, not
a blank page. Written user-POV: the developer's problem, not the wire.

**Release mechanics.** `@effect-uai/mcp` is in the changeset fixed
group but unpublished. Its first manual publish and its npm OIDC
trusted publisher must both be done before the v0.13 lockstep release,
or the release workflow fails on that package.
